1. Synthèse exécutive
Le dépôt matrixcube-1/opengraph est un système d'arbitrage FX à chemins ouverts implémenté 
en Rust (60,5 %) et Python (37,5 %), avec un adapter cTrader et un adapter FIX 4.4 en cours. Le projet 
pratique  une  honnêteté  documentaire  remarquable  :  cinq  rapports  d'audit  internes  
(REVUE_CRITIQUE,  CORRECTIONS_LOG,  AUDIT_OPERATIONNEL,  HOLDOUT_2026-10-27,  
RAPPORT_INSAMPLE) détaillent chaque bug avec cause racine, symptôme, chaîne causale, correctif,  
tests de régression et artefacts empoisonnés archivés.
Cependant, trois bugs historiques majeurs (R6, R7, Convention A) ont tous gonflé artificiellement 
le P&L du système — le pattern classique d'un agent IA (Devin AI, co-auteur de 100 % des commits) qui 
« a l'air de comprendre » sans comprendre, et qui produit du code qui a l'air de marcher parce que les 
chiffres sont positifs. Chaque bug n'a été détecté que par un audit externe ultérieur, jamais par les  
tests unitaires en place.
Verdict consolidé
• Rigueur de traçabilité exceptionnelle pour le genre (5 rapports d'audit, invariants non 
négociables numérotés, artefacts empoisonnés archivés).
• Bugs critiques historiques (R6, R7, Convention A) ont tous gonflé le P&L — pattern 
caractéristique d'erreurs subtiles d'agent IA.
• Cycle « Devin génère → audit externe → Devin corrige » fonctionne mais n'est pas systématique 
avant chaque commit.
• Aucun commit n'est signé par matrixcube-1 seul — impossible de distinguer le code revu à la 
main du code poussé directement.
• Recalibrage sous Convention A stricte encore requis avant tout mode trade (le calibrage Optuna 
actuel s'est fait sous marquage mid, donc optimiste).
• Hold-out sur jour futur complet reste bloquant pour le déploiement des paramètres calibrés sur 
corpus cTrader réel.

2. Bugs critiques historiques du moteur
Cette section détaille les trois bugs moteurs les plus graves — ceux qui ont produit du P&L  
fantôme et auraient pu passer en production sans l'audit externe. Tous ont en commun d'être des  
erreurs de logique subtiles, indétectables par les tests unitaires en place, et de gonfler artificiellement 
les résultats.
2.1 Bug R6 — Directions de chemins fantômes
Symptôme
Détecté sur cand.npz : 702 701 candidats net>0 (96 % des evals) avec max net = 23 293 396 USD 
— économiquement absurde pour un système d'arbitrage FX retail.
Cause racine
enum_paths ne conservait pas le nœud de départ du DFS. _vectorize et exec_seq supposaient  
que chaque chemin part de la base de sa 1ère arête — faux pour 5 196 chemins (50,2 %) dont le DFS  
part du côté quote.
Conséquence
Jambes partant d'un nœud non incident à l'arête → d=-1 silencieux → transitions fantômes (ex.  
JPY→USD « via » USDCHF à 1/ask) → produits absurdiment grands. Exemple : chemin π 3425 (vrai  
chemin JPY→USD→CHF→EUR) évalué à ~23,4 M$.
Fix
enum_paths retourne désormais (paths, starts) ; P_S et la marche de _vectorize, ainsi que start  
d'exec_seq, utilisent le vrai nœud de départ du DFS.
Vérification
• 0 transition fantôme sur les 10 360 chemins après correction.
• π 3425 = JPY→USD→CHF→EUR (vrai chemin) après correction.
• Artefacts invalides conservés pour audit : cand.npz.buggy_r1, optuna.db.buggy_r1.
2.2 Bug R7 — Fuite d'état inter-trials + quote future
Symptôme
Trials Optuna ≥1 affichaient ~262 $/trade constant → objectif 0,4–28,5 M$ incompatibles avec le 
scan (max 119,76 $). Baseline honnête (eng frais) : 436 k$.
Audit matrixcube-1/opengraph — 10 nov. 2026
Scan bugs — opengraph — page 8 / 25
Chaîne causale (4 maillons)
• objective_factory partage un seul Engine entre tous les trials.
• _advance (self.pos) ne pouvait qu'avancer — jamais remonter. Au replay du jour 22 après le jour 
23 (trial ≥1), les curseurs restaient en fin de données → état « figé » fin jour 26 exposé pour 
tout le jour 22.
• tick/sync posaient la quote même quand ts[j] > t (quote future).
• Fraîcheur unilatérale (t - last_t <= fresh_ms) : last_t futur → passe.
Résultat
Évaluations fantômes ; exec_seq remplissait les jambes aux vraies quotes (quote_at stateless)  
mais marquait les résidus via usd_price figé → biais de marquage systématique ~+0,26 % → 262  
$/trade.
Reproduction chiffrée
mêmes params T1 sur eng frais → 58 484 $ (j22+j23) vs 10 520 804 $ en DB (ratio 
~180×) Intermediates T1 : j22 live = 6 680 852 $ vs 57 750 $ rejoué
Correctifs appliqués (poc_engine.py)
• _advance : rembobinage par searchsorted quand pos est en avance sur t.
• tick/sync : quote exposée seulement si j >= 0 and ts[j] <= t, sinon NaN.
• eval_at : fraîcheur bilatérale (last_t <= t) & (t - last_t <= fresh_ms).
Tests de régression (test_r7.py)
• T1 : pas de quote future (AUDCHF 1er tick +4h).
• T2 : chemin sans donnée non sélectionnable.
• T3 : quote futur+500ms rejetée.
• T4 : rembobinage j23→j22 re-expose les vrais ticks.
• T5 : eval nominale inchangée.
• T6 : rejouabilité j22|j23|j22 sur même eng → identique.
Artefacts empoisonnés
optuna.db (trials T1+) archivé sous buggy_r2, non supprimé — conservé pour piste d'audit.

4. Bugs documentaires (REVUE_CRITIQUE.md)
Audit indépendant du 25 octobre 2026 sur les 4 documents canoniques (Constitution v2.2 79 p., 
Document scellé 69 p., Disponibilité Ticks Dukascopy 6 p., Simulation Monte-Carlo 6 p.). Méthode :  
lecture  intégrale  +  vérifications  indépendantes  (énumération  DFS  recodée  de  zéro,  recalcul  des 
formules, spot-checks croisés).
4.1 Findings critiques (5)
C1 — Coût de sortie du résiduel absent (marque mid non réalisable)
DDD = S × P_arrivée − P_départ avec P = mid de marquage, alors que les jambes sont aux prix  
exécutables. Le résiduel est marqué à un prix non exécutable : chaque arrivée est gonflée de ≈ ½-
spread de sa devise/paire (~0,5–4 USD/100k).
Coût_total (§8.3) = entrée + portage + base + conversion + div/roll — aucune provision de sortie. 
Le seul aveu : D-10 (coûts de sortie manquants de l'optimal stopping), jamais reporté sur la règle  
d'envoi.
Conséquence : « ENVOYER  DDD_eff > Coût_total » compare une marque mid à des coûts⇔  
d'entrée. Le vrai break-even ≈ +1 jambe de coût (~7,3 USD) + ½-spread de marquage — soit quasiment 
tout le net canonique 8,07 USD.
Statut : corrigé via Convention A stricte (liquidation exécutable). Voir bug 2.3.
C2 — Atomicité / risque de jambe non modélisé
« Exécution quasi simultanée » posée (§1) mais aucune des 38 règles ne borne l'écart entre fills, 
ne traite le fill partiel/rejet (requote,  last-look)  ni ne spécifie un repli (unwind, timeout, hedge  
d'urgence).
Corollaire : pas de fraîcheur par jambe dans la règle d'envoi — des ticks asynchrones peuvent  
fabriquer un DDD fantôme (classe de bugs connue, cf. expérience Spread Arbitrage de l'utilisateur).
Statut : corrigé via Addendum R2 (règles E1-E9) + implémentation exec_seq.
C3 — Double-comptages résiduels (classe F06)
• Impact compté deux fois : DDD_eff = DDD_th − ησQ√L (§7.2) ET Coût_total inclut Glissement 
défini explicitement comme Impact ησQ√L (Tableau 8.4). Le pseudo-code reproduit le bug. Net 
faussé de 2×ησQ√L.
• Spread du bout compté deux fois en Convention A : Coût_bout (spread CFD) dans Coût_total 
inconditionnellement, alors que « le DDD d'un bout CFD inclut le spread » (§7.1).
Audit matrixcube-1/opengraph — 10 nov. 2026
Scan bugs — opengraph — page 13 / 25
• Ambiguïté r(e) : défini « taux exécutable net de frais » (§0) — si littéral, les commissions du 
Coût_total sont double-comptées.
Statut : corrigé (r(e) → « taux exécutable bid/ask brut » ; Glissement → « résiduel mesuré, ne  
pas recompter l'impact déjà dans DDD_eff » ; Coût_bout → « conv. A : frais seuls — spread dans DDD 
»).
C4 — Chaîne de calibration invalide en l'état
• Proxy venue : Dukascopy = feed ECN ≠ prix exécutables IC Markets Raw. Ce qui ne transfère 
pas : spreads exécutables, fréquence/durée des incohérences internes, slippage, latence.
• Résolution : échantillon principal prévu en barres M5 OHLC — insuffisant pour une décision ~50 
ms. dukascopy-node -t tick fournit ms mais protocole de synchronisation inter-symboles 
toujours à spécifier.
• Synchronisation : reconstituer des états simultanés exécutables sur 28 paires + bouts depuis des 
fichiers .bi5 asynchrones = protocole d'alignement non spécifié → risque de désalignements 
artificiels (faux signaux).
• CME : aucune source (Databento/DataMine cités sans audit) → la moitié du dual-venue n'est 
pas calibrable.
Statut : partiellement mitigé (ticks ms via fetch_poc.py) mais la synchronisation inter-symboles 
reste un point ouvert critique (E3 dans AUDIT_OPERATIONNEL).
C5 — La simulation Monte Carlo ne prouve pas ce qu'elle prétend
• Tautologies : 11 « contrôles analytiques » invérifiables-faux-par-construction (Score≡DDD = 
même expression ; « 30>21,93→True » teste > ; « identité exacte » code vs lui-même).
• Faux positifs jamais testés : send rate 0,000 % hors edge_injected — le filtre n'est éprouvé que 
sur des edges injectés (circulaire).
• P(net<0|sent)=0,00 % est mécanique (un chemin envoyé a par construction DDD>coût sur les 
mêmes prix).
• Mean net (tous) = −4,20 = moyenne contrefactuelle du meilleur chemin — non défini, présenté 
comme un P&L.
• chemins = 3 108 vs 3 112 attendu — convention défendable mais non documentée et différente 
du dénombrement scellé.
• Écart send rate A (0,5667 %) vs B (0,6083 %) ~7 % relatif non expliqué → suggère asymétrie 
demi-spread/spread complet — précisément le piège F06.
• Manquent : risque de jambe, latence, coût de sortie, granularité CME, Hawkes dynamique (λ 
constant), filtrage effectif de p_persist.

5. Bugs opérationnels
5.1 Incident de pollution de données (30 octobre 2026)
Symptôme
Un processus fetch_poc.py lancé le 27/10 restait actif dans le tarpit WAF, rebouclait ses repasses 
et réécrivait les CSV des 3 jours POC (317 fichiers entre 13 h et ~19 h UTC).
Impact
Un run lisant un fichier à mi-écriture voyait une heure tronquée → état moteur divergent →  
argmax d'eval différent au même t. Preuve : GBPUSD/−3.73 vs AUDJPY/−2.66 à t=1792724877113,  
comptes de ticks différant de 17 104.
Conséquences classées
• Valables : écarts appariés (0 flip, PnL bit-identique), mesures temporelles (ns), runs antérieurs 
au 30/10 13 h.
• Suspects : exec counts et PnL globaux des runs du 30/10 ≥13 h, incluant anomalies d'execs de la 
grille D.
• Action : re-validation des chiffres clés sur données gelées (ladder7).
Règle ajoutée
Un seul downloader à la fois — et aucun run d'analyse pendant qu'un fetcher écrit dans  
/opt/arb/data.

8. Verdict consolidé
8.1 Bon signe — maturité de la traçabilité
Le projet pratique une honnêteté documentaire exceptionnelle : 5 rapports d'audit internes  
détaillent chaque bug avec cause racine, symptôme, chaîne causale, fix, tests de régression, et  
artefacts empoisonnés archivés. Verbatim de la REVUE_CRITIQUE : « Corpus d'une rigueur et d'une  
traçabilité exceptionnelles pour le genre. »
8.2 Mauvais signe — bugs profondément révélateurs
Les  bugs  R6,  R7  et  Convention  A  sont  des  erreurs  de  logique  subtile  que  seul  un  audit 
indépendant pouvait détecter :
• R6 : un DFS qui ne conserve pas le nœud de départ → 50 % des chemins évalués avec la 
mauvaise direction → P&L fantôme jusqu'à 23 M$.
• R7 : un moteur qui ne rembobine pas entre trials → curseur figé en fin de données → quote 
future exposée → P&L fantôme de 10,5 M$.
• Convention A : marquage au mid au lieu des prix exécutables → holdout gonflé de +955 $ à 
+61,58 $ une fois corrigé.
Ces 3 bugs ont tous gonflé artificiellement le P&L. C'est le pattern classique d'un agent IA qui « a 
l'air de comprendre » sans comprendre — et qui produit du code qui a l'air de marcher parce que les  
chiffres sont positifs.
8.3 Risque résiduel principal
Le cycle « Devin génère → audit externe → Devin corrige » fonctionne, mais :
• Chaque audit a révélé des bugs critiques qui auraient pu passer en prod sans lui.
• Les audits ne sont pas systématiques avant chaque commit.
• Aucun commit n'est signé par matrixcube-1 seul → impossible de distinguer le code revu à la 
main du code poussé directement par Devin.

8.5 Recommandation finale
Le système est techniquement mature côté code (parité bit-exacte Python/Rust, 60 tests  
cTrader,  gates  perf  validées)  mais  n'est  PAS  encore  prêt  pour  le  live  trading.  Les  conditions 
bloquantes sont :
• Recalibrage sous Convention A stricte (le calibrage actuel est optimiste).
• Hold-out jour futur complet sur corpus cTrader réel.
• Durcissement SSH avant prod.
• Spécification de la synchronisation inter-symboles (E3).
• Mise en place d'une revue humaine obligatoire avant tout commit de Devin sur le cœur métier.
Sans ces 5 conditions, le système présenterait un risque de perte en capital réel supérieur à ce 
que les chiffres auto-rapportés suggèrent.
